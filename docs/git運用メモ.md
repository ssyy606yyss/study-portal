# Git 運用メモ(ブランチの切り方)

## 結論

このリポジトリ(一人で使う学習用サイト)では、**develop ブランチは作らなくてよい**。

## なぜ develop が要らないか

develop ブランチを使うのは **Git Flow** というやり方で、次のような場面向け。

- 複数人が並行して開発する
- 「本番用(main)」と「開発の統合用(develop)」を分けて、リリース時期を管理したい

このリポジトリは、一人で使う・リリースの区切りが無い・main がそのまま最新版、という条件。
develop を足してもマージの手間が増えるだけで、メリットが少ない。

## このリポジトリでの進め方

| 変更の大きさ | やり方 |
|---|---|
| 小さな変更(文章修正、ファイル追加など) | main に直接コミットしてプッシュ |
| 大きめ・実験的な変更 | 作業ブランチを切る → 確認 → main にマージ(必要なら PR) |

作業ブランチを切る方式を **GitHub Flow** と呼ぶ(main + 短い作業ブランチだけで運用する)。

### 作業ブランチの流れ(例)

```bash
git switch -c add-xxx          # 作業ブランチを作る
# ... 編集してコミット ...
git push -u origin add-xxx     # ブランチをプッシュ
git switch main
git merge --ff-only add-xxx    # main に取り込む
git push origin main
```

## develop を検討するタイミング

- 人が増えて、同時に複数の機能を開発するようになった
- 公開サイトとして「安定版」と「開発中」を分けたくなった

その時に作れば十分間に合う。
